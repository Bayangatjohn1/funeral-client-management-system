# Cross-page UI conventions

Use these decisions when improving a comparable panel page. Inspect the current staff source and effective styles first; these are presentation and interaction conventions, not permission to copy another page's fields, metrics or business policy.

## Page structure and hierarchy

- Keep one page title and a short, plain-English subtitle describing only that page's scope. For the approved Branch/User/Payment worklists, place the existing page action at the end of the toolbar (see the current UI ledger); keep Service Add in its section intro. Other pages retain their existing title-row action placement. Do not add a redundant topbar. When the page uses an icon-led header, show a relevant, decorative icon beside the title, with the same size and treatment as comparable pages.
- Use the staff page canvas, typography, surfaces and spacing in both themes. Follow the current decision ledger for the six record worklists: connect header/KPI summary areas where KPIs exist and connect Case/Master tabs to the header, with the toolbar/table 16px below; keep pagination separate. Main sections use 16px gaps and records/footer uses 12px. Outside those approved pages, retain comparable staff surface structure; do not wrap the entire page in an extra card. Preserve all live data and original actions.
- Before adding a KPI, verify its operational purpose and whether the same information already exists in analytics. Label its time basis clearly (for example, all-time cases versus cases recorded this month), and do not imply that an informational metric filters another page unless its destination and selected context actually work.

## Filters, lists and actions

- For current Case Records/Master Case Records controls, read the [current UI decision ledger](../../funeral-system-ui-consistency/references/current-ui-decisions.md): its latest scoped choices supersede the older generic order below. Record user revisions there in the same UI task, with implementation and verification status.
- For other comparable pages, put primary filters in task order: Search, scope (such as branch) when applicable, date, sort, More Filters, then Rows per page. Move lower-frequency filters into the existing More Filters control only when doing so preserves their options, selected state and query behavior. Keep Clear visible without creating a mostly empty extra row; show it only when filters are active.
- Each filter should have one visible outer surface and border. A nested input/select must not create an inner box. Check the actual open menu, keyboard focus, selected state, wrapping and result update—not only the static screenshot. Follow the page-specific filter reference where one exists.
- Grid and table representations of the same record must use the same icon for the same action, with consistent accessible names, tooltips, hover/focus/disabled states and meaning. Prefer distinct View (eye), Edit (pencil-square) and Disable/Enable (slash-circle/check-circle) iconography where those actions exist. Use the same status wording across card, table, detail view and confirmation. Do not add actions a role cannot perform.
- For Branch Management, User Management and Service Management (2026-11-04), Grid cards show a transparent eye plus the short visible label `View`; both glyph and label turn green together on hover/focus. Tables keep View icon-only. The primary eye glyph is18px in a40px target. Both views use a40px transparent icon-only three-dot trigger with its existing glyph size and the single tooltip `More actions`—not `View more actions`, because the control reveals a menu rather than viewing a record. View tooltips remain contextual (`View branch`, `View user`, `View {catalog}`), while record names stay in `aria-label`. One idempotent shared top-layer tooltip owner replaces native/embedded/pseudo-element page tooltips and dismisses on pointerdown/click. The opened menu uses concise icon+text items with distinct psychology colors: Edit blue, reversible negative state changes amber, positive restoration/activation green, protected actions muted. Color applies only to text/icon, never an action background. Preserve every route, confirmation, role check and async reinitialization. Menus use shared fixed positioning and flip above near the viewport bottom rather than clipping inside the table/card.
- Case Records and Master Case Records follow the View + More-actions hierarchy where authorized Edit/Print actions exist. Payment Monitoring is an explicit exception: its row has only the View eye, which opens the complete Payment History side drawer; Print and individual payment actions remain inside that drawer. Do not add a three-dot or separate row summary merely for cross-page symmetry.
- Keep table columns and live values intact. Use a restrained weight for ordinary row data; reserve stronger emphasis for identifiers or primary names. Ensure numeric values align with their headers. Wide tables scroll within their table region on narrow screens, without hiding columns or letting sticky headers cover filters.

## Modals, flow and feedback

- Reuse the existing modal/dialog shell and behavior. Modal titles have a relevant decorative icon in the header; use a context-appropriate icon for View, Add, Edit, Disable/Enable, loading and error states. Keep title, subtitle and close control aligned in both themes and at narrow widths. Do not add a second outer container around an already styled form panel.
- Use the shared viewport-wide scrim `rgba(15, 23, 42, 0.72)`, including over the sidebar. Keep footer actions grouped and separated from the close button. Preserve Escape/backdrop/close, focus return, scroll lock and existing validation behavior.
- Return Cancel/Back to the actual origin: a direct row/card action returns to the list; an action launched from a details modal returns to that details modal. Do not open a details modal after cancelling a direct action. Confirm the flow in both grid and table views where applicable.
- Show a blocking explanation only after the user selects the relevant status action or a check finds a blocker; do not show disable-policy warnings on an ordinary details view. After a successful status change, give a specific, plain-English success indication identifying the record and its new status. Ensure the resulting badge and available action reflect that status. Do not claim effects that the server has not implemented.
- For Branch/User status changes, the confirmation is not complete unless every visible trigger has a matching permission-scoped form. Show an immediate pending verb after submit (Disabling/Enabling or Deactivating/Activating), disable the submit control and expose `aria-busy`. Branch preflight explanations and User account safeguards remain server-owned. Async directory replacement must refresh confirmation markup together with records, without registering duplicate delegated listeners.
- Branch/User confirmation feedback follows the shared lightweight dialog hierarchy and existing 50% black dim scrim. Use green for Enable/Activate, amber for reversible Disable/Deactivate, and red only for an actual blocker/error—not for the normal reversible confirmation. Use a neutral Cancel/Close, identify the affected branch/user in the dialog and resulting success/error message, keep viewport-bounded scrolling, return focus, and retain every permission/preflight safeguard.

## Verification before reporting completion

- Compare the changed page with the actual staff reference at matching desktop, intermediate and mobile widths in light and dark modes. Exercise the changed controls, open states, tooltips, modal flows, validation and post-action feedback with isolated test data where writes are involved. A build or source inspection alone is not visual verification.
- Run the relevant build, Blade and focused workflow tests required by the main skill. Check the rendered browser state, including layout overflow, icon visibility and click targets, before declaring visual parity. Report any states that could not be tested rather than assuming they work.
