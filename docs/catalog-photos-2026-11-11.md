# Optional catalog photos

Service Management now supports one optional JPG/PNG photo per package, casket, hearse, add-on and freebie. Choose File and the existing signed phone QR flow both populate the same native file field; no phone login is needed. QR sessions last five minutes and accept one file. Catalog staging uses catalog-photo-uploads, separate from payment proof storage. Final photos use private catalog-photos storage and authenticated admin preview routes.

System Admin can upload/replace/remove; Branch Admin is read-only and cannot read another branch's chapel photo. Staff cannot access the catalog-photo endpoint. Original item/price/status validation and edit permissions remain in place. Files are checked again at save: JPG/PNG, up to 5 MB, decoded image dimensions up to 8000px per side. User-supplied storage paths are ignored.

The optional Photo section follows basic form details. Saved photos have a preview, Replace Photo and Remove Photo with undo. Remove/replace takes effect on Save; Cancel preserves the old file. A failed validation or database save preserves the saved photo, while a failed new file is cleaned up. Successful replacement deletes the old file only after commit. Pending QR/transfer prevents an accidental save. New upload sessions that are abandoned remain subject to the existing temporary-upload cleanup job.

Package and catalog grid cards use a responsive 16:9 cover image with a centered crop. Empty cards reserve the same neutral media area. Table names have compact thumbnails, and drawers support a larger preview with zoom/Fit to View. Tables and drawers display a photo when one is saved. Packages use their own optional photo from Basic Details across the grid, table, drawer and brochure. Linked caskets and hearses display as inclusion text. Reference synchronization includes all five private photo paths; all participating deployments need the new migration and updated sync code. The brochure/menu print implementation now reuses these photos; see service-brochure-print-2026-11-11.md.

The single new migration was applied locally. Checks: 60 isolated SQLite runtime checks and 44 actual-Blade browser-fixture checks passed; five existing Node discard/save regressions passed. Light/dark and narrow fixture screenshots were inspected. Build, Blade compilation, route registration, PHP/JS syntax and whitespace checks passed. Feature tests are in tests/Feature/CatalogPhotoTest.php, but PHPUnit could not start because its Windows bootstrap readability check rejects vendor/autoload.php in this environment. Physical phone/LAN capture and full live-session synchronization remain unverified.
